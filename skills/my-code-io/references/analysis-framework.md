# 分析框架

根据入口类型和对话上下文，确定分析模式。以下四种模式可组合使用，但必须明确主次。

## 模式判断

| 入口 | 对话上下文 | 主模式 |
|------|-----------|--------|
| 文件/目录路径，无前置编码 | 用户刚打开项目或说"介绍一下" | 静态分析 |
| 文件/目录路径，前文已编码或 debug | 用户在开发过程中想总结某模块 | 模块深挖 |
| 功能描述（非路径） | 用户说某功能有问题或想了解 | 问题追踪 |
| 为空，前文有大量编码/debug | 用户说"总结一下"或类似 | 过程复盘 |

以下四种模式分别描述。SKILL.md 步骤 2 执行分析时，按主模式优先，必要时混合。

---

## 模式一：静态分析（默认）

从顶层出发，介绍"这个项目是干什么的"。

### 入口选择

- 若 `<entry>` 是目录 → 先读该目录的入口文件（`main.py`/`index.js`/`CLAUDE.md`/`README.md`），再按调用链下钻。
- 若 `<entry>` 是文件 → 先读该文件，再横向展开依赖。
- 若 `<entry>` 为空 → 从项目根目录的 README 和顶层模块开始。

### 分析维度

递归追踪引用和依赖，优先核心逻辑，跳过第三方依赖和生成代码。从以下维度库中选取 **4-8 个最相关的**，不必全用。选取原则：利于受众理解、适合当前介绍目的。

#### 架构与结构

- **整体架构**：模块划分、分层结构、目录职责。画出顶层到底层的调用链。
- **调用关系**：函数/模块间的调用链、上游下游、同步异步。
- **设计模式与抽象**：重要的基类/接口、工厂、策略、中间件等。
- **依赖拓扑**：外部依赖（第三方库/框架/平台）和内部模块间的耦合关系。

#### 业务与领域

- **业务问题**：这个项目解决什么用户问题，一句话说清定位。
- **核心领域概念**：关键的实体、术语、业务流程。读者需要先理解这些才能读懂代码。
- **业务规则与约束**：隐含的假设、校验逻辑、状态机、权限模型。

#### 数据

- **数据流**：数据从哪来、经过哪些处理、到哪去。
- **持久化与存储**：数据库选型、Schema 设计、缓存策略、文件组织。
- **数据转换**：序列化/反序列化、ETL、格式转换、编码解码。

#### 接口与交互

- **对外 API/CLI**：命令列表、参数说明、输入输出格式。
- **内部接口**：模块间约定的函数签名、RPC 定义、消息格式。
- **配置与扩展点**：环境变量、配置文件、插件机制、开关。
- **事件与消息**：事件总线、消息队列、Webhook、回调机制。

#### 质量属性

- **性能特征**：吞吐量、延迟、资源占用、瓶颈位置和优化策略。
- **安全模型**：认证、授权、加密、输入校验、防护措施。
- **可靠性与容错**：重试、降级、熔断、事务、数据一致性保证。
- **可测试性**：测试策略（单元/集成/E2E）、Mock 方式、测试辅助工具。

#### 工程实践

- **构建与部署**：构建流程、CI/CD 配置、容器化、发布策略。
- **日志与监控**：日志级别与格式、指标采集、告警规则、调试入口。
- **错误处理**：异常分类、错误码约定、错误传播与恢复策略。
- **代码组织**：命名规范、目录约定、代码风格、注释策略。

#### 演进与背景

- **历史与动机**：为什么这样设计，经历了哪些重构和权衡。
- **技术选型理由**：为什么选这个框架/库/语言，对比过哪些替代方案。
- **已知局限**：当前版本的边界、不支持的场景、技术债务。
- **未来方向**：Roadmap、待实现的功能、计划中的重构。

#### 使用者视角

- **快速开始**：最小可运行示例、环境准备步骤、hello-world 路径。
- **典型工作流**：常见操作步骤、日常使用场景。
- **常见陷阱**：容易出错的地方、FAQ、已知兼容性问题。

#### 规模与复杂度

- **代码量分布**：各模块/目录的行数、文件数、复杂度趋势。
- **热点与瓶颈**：修改频率最高的文件、最复杂的函数、耦合最紧的模块。

### 维度选取指导

选取时考虑三个因素：
1. **受众**：技术人员关注架构/接口/性能；非技术读者关注业务/流程/快速开始。
2. **目的**：介绍项目全貌 → 架构+业务+数据；解释某个模块 → 接口+内部实现+依赖；复盘总结 → 决策+教训+局限。
3. **篇幅**：4-6 维度适合短文（< 200 行），6-8 维度适合长文。宁缺毋滥。

### 输出要求

开篇必须用一段话概括项目的定位和用途，然后按选取的维度组织章节，重要的维度优先。

## 模式二：模块深挖

用户指定了一个模块或文件，需要聚焦分析该模块的设计和实现。

### 入口选择

- `<entry>` 已指定 → 精准读取。
- 前文涉及多个文件 → 用 `question`（单选）列出候选文件，让用户选定聚焦哪个。

### 分析维度

- **定位**：该模块在整体架构中的位置和职责。
- **接口**：对外暴露的函数/类/方法签名，输入输出契约。
- **内部实现**：核心算法、关键逻辑、异常处理。
- **依赖**：上游谁调用它，下游它调用谁。
- **边界条件**：特殊输入、并发、事务、性能瓶颈。

### 输出要求

先说明该模块的定位（一句话），再按"接口→实现→依赖→边界"展开。

---

## 模式三：过程复盘

对话中进行了大量编码或 debug 操作，需要记录方案尝试、决策和踩坑过程。此模式的信息来源是**对话历史**而非代码文件。

### 信息收集

回顾当前会话中的关键节点：
- 用户最初的需求或问题是什么。
- 尝试了哪些方案、各自的结果（成功/失败/部分成功）。
- 每个方案被采纳或放弃的原因。
- 最终方案的完整步骤和关键代码变更。
- 过程中踩到的坑、意外发现、值得记住的教训。

### 输出要求

按时间线或决策树组织，强调"为什么"而非仅"做了什么"。适合作为项目记忆或后续参考。

---

## 模式四：外部信息

某些问题涉及项目外部的内容（依赖库行为、API 文档、社区方案等）。

### 获取策略

1. **已有上下文优先**：先检查对话历史和已读取文件中是否已有答案。
2. **搜索**：若需要最新文档，用 `WebSearch` 或 `context7` 查询。
3. **推测与标注**：基于已有信息可以做靠谱推测，但必须明确标注"（推测）"或"（待确认）"。
4. **确认**：关键结论写入文章前，用 `question`（多选）列出各推测点让用户勾选确认为事实的部分，未勾选的保留"（推测）"标注，不自行认定为事实。

---

## 通用约束

- 优先读取核心逻辑文件，跳过第三方依赖、生成代码、二进制。
- 不修改当前工作目录下任何文件。
- 基于代码和对话事实写作，不确定的地方标注推测而非断言。
