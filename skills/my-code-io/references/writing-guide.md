# 撰写规范

## 大纲规划（步骤 3）

- 标题层级最多 5 层（`#####`）。
- 内容排序：业务优先于技术，架构优先于细节；关键的技术细节可提前着重写。根据实际重要程度调整章节顺序。
- 章节取舍：不重要或内容不足的章节直接省略，不填充冗余内容。
- 超 300 行时用 `question`（单选）让用户选择：合并为一篇 / 拆分为多篇。

## 多篇拆分（步骤 7）

- 每篇聚焦一个主题（如"架构概述"、"核心流程"、"数据与存储"）。
- 每篇开头列出系列中其他文章的链接。
- 每篇单独用 `question` 确认大纲后再撰写保存。

## 语言与读者

- 中文为主，代码符号、类名、函数名、关键概念保留英文原文。严谨准确，避免口语化。
- 读者具备基本技术常识，但不了解项目技术栈和业务背景。开篇先解释"这个项目是干什么的"。
- 说明"为什么"而非仅"是什么"：解释设计意图、业务背景。

## 代码引用

- 关键代码片段不超过 25 行，用 Markdown 代码块并标注语言。
- 引用前加一句解释该代码做了什么。
- 标注文件出处（项目根目录的相对路径）。
- 避免大段粘贴，优先简洁描述 + 短小关键片段。
- 源码无注释时可在代码块内添加注释；已有丰富注释则不修改，改为正文补充说明。
- 某模块预计超 80 行章节时，提示拆分为独立文章。

## 图表（步骤 5）

文章中所有 mermaid 图**一律经 `Skill` 工具调用 `my-mermaid` 生成，不得自行手写 mermaid 代码，也不 `Read` type-index 自行选型**——图类型选择与配色是 my-mermaid 的职责。my-code-io 只判断哪里需要图、该图表达什么，把这段内容描述传给 my-mermaid，拿回带配色代码直接嵌入。

初级分流：tree 类（目录树、层级结构）、极简无分支线性流程等简单内容用 ASCII——必须先 `Read` `references/ascii-diagram.md` 按其规范绘制（含汉字宽度规则与转 my-mermaid 的二次分流出口）；其余一律交 my-mermaid。每张图前用一句文字说明它表达什么、如何阅读。
